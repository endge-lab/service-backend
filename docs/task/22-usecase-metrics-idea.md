# 22. Эволюция use-case metrics и Observer

## Цель

Сохранить общий `Observer` независимым от реализации метрик и одновременно
дать use case возможность записывать специализированные бизнес-метрики без
расширения общего контракта `Record`.

Архитектура должна позволять использовать один экземпляр реализации метрик
как для общих operation metrics, так и для доменных business metrics.

---

## Граница задачи

* Общий `Observer` остаётся инфраструктурным компонентом.
* `Observer` знает только о контракте `Recorder`.
* Специализированные business metrics используются только внутри
  соответствующего use case.
* Один экземпляр реализации метрик создаётся через DI и используется повторно.
* Existing operation metrics продолжают работать без изменения поведения.

---

## Проблема

Текущий общий метод `Record` покрывает только технические метрики операции:

* количество вызовов;
* длительность;
* успешное или ошибочное завершение.

Однако этого недостаточно для фиксации бизнес-событий, например:

* проект создан;
* проект восстановлен;
* проект удалён;
* импортированы компоненты;
* изменено состояние сущности.

Попытка расширять общий `Record` дополнительными параметрами приводит к
размытию его ответственности и усложнению API.

---

## Архитектурный принцип

Общие operation metrics и business metrics являются разными уровнями
наблюдаемости.

`Observer` отвечает только за жизненный цикл выполнения операции.

Доменные метрики отвечают за фиксацию завершённых бизнес-событий.

---

## Контракты

### Общий Recorder

```go
type Recorder interface {
    Record(
        ctx context.Context,
        operation string,
        startedAt time.Time,
        err error,
    )
}
```

Этот контракт используется исключительно `Observer`.

---

### Доменные метрики

Каждый модуль при необходимости объявляет собственный интерфейс.

Например:

```go
type ProjectMetrics interface {
    Recorder

    ProjectCreated(ctx context.Context)
    ProjectRestored(ctx context.Context)
    ProjectDeleted(ctx context.Context)
}
```

Добавление специализированных методов допускается только при наличии
реальной бизнес-потребности.

---

## Реализация

Конкретная реализация должна:

* реализовывать `Recorder`;
* реализовывать интерфейс доменных метрик;
* содержать регистрацию всех необходимых Prometheus collectors.

Например:

```go
type prometheusProjectMetrics struct {
    ...
}
```

---

## Dependency Injection

Реализация создаётся только один раз.

Например:

```go
projectMetrics := NewProjectMetrics(...)
```

Полученный экземпляр используется повторно.

---

## Использование

В `Observer` объект передаётся как `Recorder`.

```go
observer := NewObserver(
    logger,
    tracer,
    projectMetrics,
)
```

В соответствующий use case этот же экземпляр передаётся как
`ProjectMetrics`.

```go
usecase := NewProjectUsecase(
    repository,
    observer,
    projectMetrics,
)
```

Повторное создание реализации не допускается.

---

## Использование в use case

Общие operation metrics продолжают записываться через `Observer`.

Например:

```go
defer observed.End(&err)
```

или существующим механизмом завершения операции.

Доменные события записываются напрямую через специализированный интерфейс.

Например:

```go
u.metrics.ProjectCreated(ctx)
```

или

```go
u.metrics.ProjectRestored(ctx)
```

после успешного завершения соответствующего бизнес-действия.

---

## Ограничения

* Не расширять общий `Record` специализированными параметрами.
* Не добавлять бизнес-методы в `Observer`.
* Не создавать несколько экземпляров реализации метрик.
* Не регистрировать Prometheus collectors повторно.
* Не передавать concrete Prometheus implementation вместо интерфейсов.
* Не переносить business metrics внутрь общего operation recorder.

---

## Эволюция архитектуры

Изначально система содержала только общий `Recorder`, поскольку требовались
исключительно operation metrics.

После появления требований к доменным business metrics архитектура была
расширена без изменения существующего `Observer`.

Такой подход сохраняет обратную совместимость и позволяет постепенно
расширять наблюдаемость отдельных bounded context без изменения общей
инфраструктуры.

---

## Проверка

После внедрения необходимо проверить:

1. `Observer` продолжает работать только с интерфейсом `Recorder`.
2. Один экземпляр реализации используется одновременно как:

    * `Recorder`;
    * доменный интерфейс метрик.
3. Business metrics корректно записываются из use case.
4. Existing operation metrics продолжают записываться без изменений.
5. Prometheus collectors регистрируются единожды.
6. Добавлены compile-time проверки реализации интерфейсов.

Например:

```go
var _ Recorder = (*prometheusProjectMetrics)(nil)
var _ ProjectMetrics = (*prometheusProjectMetrics)(nil)
```
