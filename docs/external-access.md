# Внешние права

Начиная с backend `0.17.0`, источник назначений выбирается конфигурацией при
запуске. При отсутствии стандартного файла и `ACCESS_CONFIG_FILE` действует
`local`. Валидный файл включает `external`. Локальных override во внешнем режиме
нет. Frontend может прочитать режим из session response; новый интерфейс прав
реализуется отдельно.

## Настройка

1. В локальном режиме создайте workspace, используемые в правилах.
2. Настройте OIDC issuer, JWKS, audience и browser login через существующие
   `AUTH_*`. `AUTH_MODE` и `AUTH_LOGIN_ADAPTER` должны быть `oidc`.
3. Скопируйте [endge-access.example.yaml](../endge-access.example.yaml) в
   `endge-access.yaml` рядом с бинарником либо задайте `ACCESS_CONFIG_FILE` с
   абсолютным путём. Имя `.example.yaml` само по себе режим не включает.
4. Замените provider ID, название источника, identity workspace и имена claims
   на значения своей среды. `provider` должен совпасть с `AUTH_PROVIDER_ID`.
5. Перезапустите все экземпляры backend, работающие с одной БД, с одинаковой
   конфигурацией. Смешивать режимы и версии правил на разных экземплярах нельзя.

Пример запуска:

```bash
ACCESS_CONFIG_FILE=/etc/endge/endge-access.yaml /opt/endge/service-backend
```

Файл не содержит пользователей, токенов или credentials. Его правила хранятся
в памяти процесса и не перечитываются на каждом запросе. Явный отсутствующий
путь, нечитабельный или пустой файл, неизвестные поля/версия/адаптер,
дублирующиеся YAML-ключи и неверные типы завершают запуск ошибкой. При отсутствии
env override только действительно отсутствующий стандартный файл означает
локальный режим; сломанная символическая ссылка не считается отсутствием.
YAML aliases, merge keys и `null` не поддерживаются.

## Правила

Поддерживаются `version: 1`, `adapter: oidc`, `claimsSource: access_token` и один
provider. Каждый элемент `rules` содержит уникальный `id`, условие `when` и
назначение `grant`. `rules: []` разрешён: любой корректно аутентифицированный
пользователь получает пустой набор прав.

`when.path` — JSON Pointer, например `/resource_access/endge-configurator/roles`
или `/abac/configurator/workspaces/operations/edit`. Escape `~1` означает `/`,
`~0` — `~`; wildcard и автоматического поиска по дереву нет. Поддерживается
ровно один оператор:

- `contains` проверяет точное наличие строки в массиве строк;
- `equals` сравнивает строку, boolean или число с сохранением типа.

Отсутствующий claim, неподходящий тип или несовпавшее значение не дают роль.
`true` отличается от строки `"true"`. Все правила проверяются независимо от
порядка. Для одного workspace выбирается `admin > editor > viewer`.

`scope: platform` принимает только `role: admin`, без `workspace`. Это
Platform Admin с доступом ко всем workspace. `scope: workspace` требует
identity существующего активного workspace и одну из трёх ролей. Workspace
Admin не становится Platform Admin, а Viewer не ограничивает общую роль
Platform Admin. Неизвестный или неактивный workspace в совпавшем правиле
прерывает синхронизацию целиком.

## Вход, refresh и Bearer

При browser login backend отдельно проверяет identity и access token и
сопоставляет provider, issuer и subject. Для маппинга используется access token,
даже если identity получена из ID token. Callback синхронизирует назначения до
выдачи cookie. Refresh обновляет проверенный снимок до следующего защищённого
запроса. Bearer проходит ту же проверку и синхронизацию.

Access token должен пройти проверки подписи, алгоритма, issuer, audience,
`kid`, subject и `exp`, а также содержать `iat`. Отсутствующий `iat`, истёкший
токен или `iat` более чем на 30 секунд в будущем отклоняются. Настройте provider
так, чтобы требуемые claims попадали в access token и обновлялись при refresh.
Raw access token и исходные claims не сохраняются в БД и не возвращаются UI.
В server session сохраняется только производный маппинг с его версией,
временем выдачи/истечения токена и SHA-256 fingerprint.

Транзакция подготовки текущего пользователя сериализует запросы одной identity
через блокировку строки `service_users`. В ней заменяются `access_grants`,
совместимая проекция `workspace_memberships` и watermark `external_access_states`.
При ошибке запись откатывается, защищённый запрос не продолжает работу со
старыми ролями. Набор другого пользователя не изменяется.

Повторный запрос с тем же обработанным токеном не переписывает назначения.
Токен с `iat` меньше применённого watermark получает
`403 external_access_stale`: нужен refresh или новый вход. Два разных токена
с одинаковым `iat`, но разными итоговыми правами при тех же правилах, дают
`403 external_access_ambiguous`; порядок доставки не выбирает победителя.
Нужно получить токен с более поздним `iat`. Это явная граница для провайдеров,
выдающих несколько токенов в одну секунду.

Проверка JWT локальна: изменение прав у provider не отзывает уже выданный токен
мгновенно. Допустимая задержка ограничена его сроком действия; новый токен
применяет изменённые права. Длительные Bridge-соединения сохраняют существующую
проверку expiry и текущей роли перед операциями; heartbeat не продлевает доступ.

## API и переходы режима

Режим отражается в `GET /api/session/me` (и существующих alias session endpoint):

```json
{
  "accessManagement": {
    "mode": "external",
    "sourceName": "Корпоративный Keycloak",
    "lastSynchronizedAt": "2026-09-09T09:05:00Z"
  }
}
```

Это фрагмент ответа. Пользователь и эффективные роли остаются в существующих
`user`, `platformAdmin`, `workspaces`. В local возвращается `{"mode":"local"}`.
Метаданные синхронизации относятся только к текущему пользователю.

В external публичные use case `Put/Delete/Bulk` назначений и
`PutMembership/DeleteMembership` возвращают `403 access_managed_externally`.
Workspace import/restore переносит документы и не содержит memberships или
access grants; отдельного обходного пути назначения через snapshot нет.
Редактирование остальных документов продолжает зависеть от существующих ролей.

После изменения YAML старая cookie-сессия должна получить новый access token
через refresh или пройти вход заново. Bearer заново проверяется и маппится по
текущим правилам; старый watermark не разрешает откат к более раннему токену.

При `local → external` первый допущенный запрос заменяет локальные назначения
снимком внешних прав. При `external → local` последний сохранённый набор
становится редактируемым локальным набором. Автоматический bootstrap не создаёт
аварийного администратора, если в БД уже есть история внешней синхронизации.
До отключения external убедитесь, что сохранён действующий Platform Admin.
Явные legacy `AUTH_PLATFORM_ADMIN_*` снова действуют по правилам local.
Локальная правка назначений инвалидирует прежний маркер применения: при
возврате в external даже тот же токен заново заменит изменённые локальные роли.

Миграция `000061_external_access.sql` добавляет только внутреннее состояние auth;
схема переносимого workspace не меняется. Откат этой миграции не удаляет сами
access grants. Настройка реального Keycloak и проверка ingress выполняются
отдельно от локальных тестов с тестовым OIDC provider.
