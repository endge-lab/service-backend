# Карта доменных связей

Карта описывает структурные связи, подтверждённые схемой PostgreSQL и use case-кодом.
Произвольные ссылки внутри `data` или `source` сюда не входят: их семантикой владеют
compiler и конкретный тип документа.

## Граница владения

`workspace` владеет Domain. Динамические фасеты образуют отдельные разделы контекста,
а обычные документы организуются папками:

```text
workspace
├── facets(position) → facet_documents(facet_id)
├── folders(scope=workspace) → mixed Domain documents
├── folders(scope=collection, entity_type=queries) → queries
├── folders(scope=collection, entity_type=compositions) → compositions
└── ... отдельная типизированная ветка для каждой обычной коллекции
```

Фасет не является контейнером runtime-документов. Он владеет только своими
`facet_documents`; их configuration contribution входит в effective configuration
по позиции фасета. Query, Composition и другие обычные документы остаются соседями
в том же Workspace.

## Persisted сущности

| Сущности | Непосредственное владение | Связь с папкой | Особенность |
|---|---|---|---|
| `facets` | `workspace 1 → N facets` | Нет | Позиция уникальна среди активных фасетов и задаёт порядок cascade |
| `facet_documents` | `facet 1 → N documents` | Нет | Identity уникален внутри фасета; удаление фасета каскадно soft-delete-ит документы |
| `types`, `queries`, `data_views`, `compositions`, `stores`, `streams`, `simulations`, `mocks`, `components`, `actions`, `filters`, `converters`, `computations`, `i18n_bundles`, `navigations`, `styles`, `configurations` | `workspace 1 → N documents` | `document N → 0..1 folder` допустимого scope | Общий lifecycle: create, patch, soft delete, restore и revision history |
| `updates` | `workspace 1 → N updates` | Папка типа `updates` или Workspace-папка | Обязательно ссылается на Store того же Workspace |
| `vocabs` | `workspace 1 → N vocabs` | Папка типа `vocabs` или Workspace-папка | Опционально ссылается на Auth Profile того же Workspace |
| `auth_profiles` | `workspace 1 → N profiles` | Папка типа `auth-profiles` или Workspace-папка | Хранит adapter configuration и credential references, но не secret material |
| `folders` | `workspace 1 → N folders` | `folder N → 0..1 parent folder` того же scope | Collection-папки типизированы; Workspace-папки допускают смешанные документы |

Общие поля документа — `identity`, `display_name`, `data`, `meta`, `active`,
`deleted_at`, `revision` и авторы. Внешний API использует identity; БД хранит UUID
и проверяет принадлежность структурных ссылок одному Workspace.

## Явные прикладные связи

| Откуда | Куда | Кратность | Где хранится | Правило |
|---|---|---:|---|---|
| `facet_document` | `facet` | N → 1 | `facet_documents.facet_id` | Родитель должен существовать в том же Workspace |
| `update` | `store` | N → 1 | `updates.store_id` | `storeIdentity` обязателен; цель активна и принадлежит тому же Workspace |
| `vocab` | `auth_profile` | N → 0..1 | `vocabs.auth_profile_id` | `authProfileIdentity` опционален; цель активна и принадлежит тому же Workspace |
| `folder` | `folder` | N → 0..1 | `folders.parent_id` | Родитель имеет тот же scope; для collection scope также тот же `entity_type`; циклы запрещены |
| обычный документ | `folder` | N → 0..1 | `<table>.folder_id` | Допустима системная корневая папка коллекции либо Workspace-папка |
| `workspace` | `composition` | 1 → 0..1 | `workspaces.startup_composition_id` | Startup указывает на активную Composition того же Workspace |

## Доступ и integrations

| Откуда | Куда | Кратность | Назначение |
|---|---|---:|---|
| `workspace` | `service_user` | N ↔ N | `workspace_memberships`: локальная роль `viewer`, `editor` или `admin` |
| `workspace` | `service_user` | N ↔ N | `access_grants`: доступ к Workspace; отдельно существует platform admin |
| `workspace` | `integration` | N ↔ N | `workspace_integrations`: версия и configuration включённой интеграции |
| `service_user` | документы/workspaces | 1 → N | `created_by` и `updated_by`: audit trail, а не владение |

## История, commits, releases и snapshots

Эти сущности фиксируют состояние всего Workspace, а не отдельного контекстного
раздела.

| Откуда | Куда | Кратность | Смысл |
|---|---|---:|---|
| `mutation_batch` | `document_revision` | 1 → N | Группа изменений одного серверного действия |
| `document_revision` | document | N → 1 логически | Snapshot версии; полиморфная ссылка задаётся `document_type + document_id` |
| `workspace_commit` | `workspace_commit_change` | 1 → N | Before/after revision и операция для каждого изменённого документа |
| `release` | `workspace_commit` | N → 1 | Immutable portable snapshot исходного commit |
| `workspace` | `workspace_snapshot_backup` | 1 → N | Ручные и pre-import резервные snapshots |
| `workspace` | `workspace_snapshot_import_plan` | 1 → N | Временный план с ожидаемыми generation и head sequence |

## Изменения и side effects

| Операция | Затрагиваемые сущности |
|---|---|
| Создать или изменить обычный документ | Сам документ и одна `document_revision` в `mutation_batch` |
| Создать или изменить фасет | Facet revision; reorder может атомарно изменить позиции нескольких фасетов |
| Удалить фасет | Facet и все его активные документы получают soft-delete revisions в одном batch |
| Удалить папку | Папка soft-delete; содержимое переносится в допустимого родителя, у перемещённых сущностей растёт revision |
| Создать Workspace | Workspace, integrations, системные root folders и начальный commit |
| Создать release, import или restore | Читает или изменяет набор документов Workspace как единое целое |

## Практический маршрут чтения

Для обычной ручки сначала достаточно `documents.Lifecycle`. Специализированный
use case нужен для владельцев особого контракта:

1. `facets` — ordering, nested identities и каскадный lifecycle;
2. `updates` — required Store;
3. `vocabs` — optional Auth Profile;
4. `folders` — scope, дерево и массовое перемещение содержимого;
5. `workspaces` — startup Composition;
6. `commits`, `releases`, `backups`, `domain/import` — orchestration полного состояния.

Soft delete не равен физическому удалению. История сохраняет прежние revisions,
а обычное разрешение связей принимает только активные цели.
