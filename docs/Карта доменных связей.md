# Карта доменных связей

Эта карта описывает **структурные связи, которые подтверждены схемой БД и use case-кодом**. Она не пытается интерпретировать произвольные ссылки внутри `data` или `source`: такие поля могут содержать identity других ресурсов, но для них нет общего внешнего ключа.

## Главная идея модели

`workspace` — граница владения почти всем доменным состоянием. Внутри него документы одного общего вида разделены по коллекциям: `projects`, `queries`, `converters` и т. д. Каждый такой документ имеет собственную папку, но папки **типизированы**.

```text
workspace
├── root-projects → folders(entityType=projects) → projects
├── root-queries  → folders(entityType=queries)  → queries
├── root-converters → folders(entityType=converters) → converters
└── … отдельное дерево папок для каждого типа документа
```

Следствие: проект не является контейнером для query или converter. Все три сущности — соседи в одном `workspace`; у каждой своя папка допустимого типа. Связать их через общее поле `folder_id` нельзя: папка query должна иметь `entity_type = queries`, а папка проекта — `entity_type = projects`.

## Общий каркас документных сущностей

| Сущности | Непосредственное владение | Связь с папкой | Особенность |
|---|---|---|---|
| `projects`, `tenants`, `environments`, `types`, `queries`, `data_views`, `compositions`, `stores`, `streams`, `mocks`, `components`, `actions`, `filters`, `converters`, `computations`, `i18n_bundles`, `navigations`, `styles` | `workspace 1 → N documents` | `document N → 0..1 folder` своего `entity_type` | Обычный документный lifecycle: create, patch, soft delete, restore, revision history |
| `updates` | `workspace 1 → N updates` | `update N → 0..1 folder` типа `updates` | Обязательно ссылается на `store` того же workspace |
| `vocabs` | `workspace 1 → N vocabs` | `vocab N → 0..1 folder` типа `vocabs` | Опционально ссылается на `auth_profile` того же workspace |
| `folders` | `workspace 1 → N folders` | `folder N → 0..1 parent folder` того же `entity_type` | Формирует лес типизированных деревьев; корневые папки создаются системой |

Общие поля документа — `identity`, `display_name`, `folder_id`, `data`, `meta`, `active`, `deleted_at`, `revision` и авторы. Внешнее API использует `identity`; БД хранит UUID и проверяет принадлежность ссылок тому же workspace составными FK.

## Явные прикладные связи

| Откуда | Куда | Кратность | Где хранится | Правило |
|---|---|---:|---|---|
| `project` | `folder` | N → 0..1 | `projects.folder_id` | Папка только типа `projects`; это организация проекта, не контейнер остальных типов |
| `project` | `environment` | N ↔ N | `project_environments` | `allowedEnvironments` заменяет список связей целиком; порядок хранится в `sort_order` |
| `project` | `navigation` | N → 0..1 | `projects.navigation_id` | Передаётся как `navigationIdentity`; цель обязана быть активным `navigation` того же workspace |
| `update` | `store` | N → 1 | `updates.store_id` | `storeIdentity` обязателен; цель должна быть активной и в том же workspace |
| `vocab` | `auth_profile` | N → 0..1 | `vocabs.auth_profile_id` | `authProfileIdentity` опционален; цель должна быть активной и в том же workspace |
| `folder` | `folder` | N → 0..1 | `folders.parent_id` | Родитель той же типизированной ветки; циклы запрещены |
| любой документ | `folder` | N → 0..1 | `<table>.folder_id` | При отсутствии `folderIdentity` назначается системная корневая папка типа документа |

## Workspace, доступ и интеграции

| Откуда | Куда | Кратность | Назначение |
|---|---|---:|---|
| `workspace` | `service_user` | N ↔ N | `workspace_memberships`: локальная роль `viewer`, `editor` или `admin` |
| `workspace` | `service_user` | N ↔ N | `access_grants`: workspace-доступ; отдельно существует платформенный `admin` без workspace |
| `workspace` | `integration` | N ↔ N | `workspace_integrations`: версия и конфигурация включённой интеграции |
| `service_user` | документы/workspaces | 1 → N | `created_by` и `updated_by`: аудит, а не владение |

## История, commits, releases и снимки

Это не дочерние доменные ресурсы проекта. Они фиксируют состояние **всего workspace**.

| Откуда | Куда | Кратность | Смысл |
|---|---|---:|---|
| `mutation_batch` | `document_revision` | 1 → N | Группа изменений одного действия |
| `document_revision` | документ | N → 1 логически | Снимок конкретной версии документа; полиморфная ссылка задаётся `document_type + document_id` |
| `workspace_commit` | `document_revision` | 1 → N | Commit объединяет набор ревизий; у commit есть родительский commit |
| `workspace_commit` | `workspace_commit_change` | 1 → N | Для каждого изменённого документа — before/after revision и операция |
| `release` | `workspace_commit` | N → 1 | Release ссылается на исходный commit и хранит экспорт состояния |
| `workspace` | `workspace_snapshot_backup` | 1 → N | Ручные и pre-import резервные снимки |
| `workspace` | `workspace_snapshot_import_plan` | 1 → N | Временный план импорта с ожидаемыми generation и head sequence |

## Что происходит при изменениях

| Операция | Затрагиваемые сущности |
|---|---|
| Создать / изменить обычный документ | Сам документ + одна `document_revision` в `mutation_batch`; у проекта также синхронизируется таблица `project_environments` |
| Удалить папку | Папка soft-delete; все документы и дочерние папки из неё перемещаются в родительскую папку; у перемещённых документов увеличивается revision и пишется история |
| Восстановить папку | Папка возвращается в корень своего типа, а не в прежнего родителя |
| Создать workspace | Workspace + workspace integrations + системные root-папки для типов документов + начальный commit |
| Создать release / import / restore | Работает со снимком и историей состояния workspace, поэтому меняет/читает набор документов как единое целое |

## Практический способ читать флоу

Для обычной ручки сначала достаточно понять общий `documents.Lifecycle`: он разрешает папку, сохраняет документ, применяет только структурированные связи из таблицы выше и пишет ревизию. Затем смотреть use case конкретного ресурса нужно только при наличии особых связей:

1. `projects` — environments и navigation;
2. `updates` — required store;
3. `vocabs` — optional auth profile;
4. `folders` — дерево и массовое перемещение содержимого;
5. `commits`, `releases`, `backups`, `domain/import` — orchestration полного состояния workspace.

## Границы этой карты

- `data` и `source` у многих документов содержат предметную конфигурацию. Ссылки в них могут быть семантически важны, но не выводятся из FK автоматически.
- Soft delete не равен физическому удалению: большинство связей остаётся в БД, однако обычные операции разрешения связей принимают только активные цели.
- Для полного понимания runtime-зависимостей следующей картой стоит отдельно разобрать контракты `source` у `queries`, `compositions`, `components`, `converters`, `computations` и `actions`.
