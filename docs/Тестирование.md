# Тестирование Endge Backend

## Назначение

Тесты разделены по уровню и по требованию к инфраструктуре. Обычный запуск Go-тестов
не обращается к Docker, `.env`, локальному PostgreSQL или production-базе. PostgreSQL
используется только в наборах с явными build tags `integration` и `e2e`.

Мутационное, нагрузочное и инфраструктурное production-тестирование в текущий MVP не
входят.

## Команды запуска

```bash
# Unit, contract, architecture и seed corpus всех fuzz-тестов. Docker не нужен.
make test-unit

# Репозитории, транзакции и миграции на PostgreSQL 17 в Testcontainers.
make test-integration

# Полный HTTP pipeline Fiber -> middleware -> use case -> PostgreSQL.
make test-e2e

# Последовательно запускает все три уровня.
make test-critical

# Race detector только для обычного недокерного набора.
make test-race
```

Для integration и E2E требуется запущенный Docker daemon. Порт PostgreSQL выбирается
случайно. Если Docker недоступен, явно запущенный tagged-набор завершается ошибкой:
он не превращается в `skip` и не создаёт ложный успешный результат CI.

Длительность fuzz campaign задаётся переменной `FUZZ_TIME`:

```bash
make fuzz-transport FUZZ_TIME=2m
make fuzz-documents FUZZ_TIME=2m
make fuzz-import FUZZ_TIME=2m
make fuzz-auth FUZZ_TIME=2m
```

Без `-fuzz` обычный `go test ./...` выполняет только сохранённый seed corpus. Поэтому
он остаётся детерминированным и не запускает бесконечную генерацию входов.

## Защита реальной базы

Harness расположен в [`test/support`](../test/support). Он намеренно не читает
`TEST_POSTGRES_DSN`, другие DSN, `.env` или process configuration приложения.

Для одного test package создаётся отдельный контейнер `postgres:17-alpine`. Каждый
сценарий получает новую БД с именем `endge_test_<random UUID>`. До применения
миграций harness создаёт в ней уникальный marker:

```text
endge_test_guard.database_marker
```

Перед `down` и `DROP DATABASE` одновременно проверяются:

1. префикс `endge_test_` у ожидаемого имени;
2. результат PostgreSQL `current_database()`;
3. уникальный marker, известный только текущему экземпляру harness.

Любое несовпадение запрещает destructive-операцию. После теста закрывается pool,
завершаются оставшиеся соединения и удаляется только явно проверенная БД. После
завершения package suite удаляется контейнер. Отдельный safety-тест намеренно меняет
ожидаемое имя и marker и подтверждает fail-closed поведение.

## Структура наборов

| Уровень | Расположение | Что проверяется |
|---|---|---|
| Unit | `internal/**/**_test.go` | конфигурация, OIDC/JWT, transport decoder, validator, ETag, секреты, application inputs, observability |
| Architecture | `test/architecture` | границы слоёв, владельцы таблиц, naming convention, структура transport/usecase/repository, порядок 39 миграций |
| Contract | `test/contract`, `internal/api/http/openapi` | checked-in OpenAPI, Scalar-маршруты, параметры, `If-Match`, статусы `409/428`, отсутствие исключённых коллекций |
| Integration | `test/integration` | реальные миграции, PostgreSQL constraints, repositories, транзакции, revisions, commits, squash, releases |
| E2E | `test/e2e` | реальный in-process Fiber pipeline с настоящими middleware, use cases и PostgreSQL |
| Support | `test/support` | контейнер, отдельные БД, миграции, safety marker, локальный JWKS и RSA-токены |

## Покрытые сценарии

### Миграции и PostgreSQL

- Все 39 embedded-миграций применяются к пустой БД в правильном порядке.
- Повторный `up` идемпотентен.
- Полный `down` очищает application schema; затем полный `up` проходит повторно.
- Bootstrap создаёт system user, workspace `default`, 21 системную root-папку и
  начальный commit.
- Таблицы `parameters`, `pages`, `page_templates`, `policies`, `versions`,
  `components_legacy` и dependency index отсутствуют.
- Все document repositories работают с реальным PostgreSQL.
- Искусственная ошибка после insert подтверждает rollback транзакции без остаточного
  документа.
- Искусственный PostgreSQL trigger ломает import после начала записи. Проверяется,
  что не остаются partial documents, backup или commit и что SQL-текст не попадает
  в HTTP error envelope.

### Авторизация и безопасность

- RSA/JWKS token в стиле Keycloak принимается.
- Отклоняются неверные `kid`, algorithm, issuer, audience, `sub`, `exp`, `nbf`,
  подпись, HMAC и malformed JWT.
- Production-конфигурация запрещает dev auth и неполный OIDC.
- Health доступен публично, API без пользователя возвращает `401`.
- Первый bearer-запрос создаёт локального пользователя; повторный сохраняет UUID;
  изменённый профиль синхронизируется; inactive user получает `403`.
- Изменяющие запросы с browser cookie требуют разрешённый `Origin`; bearer-запросы
  не используют cookie-CSRF правило.
- Access token не сохраняется в browser session; зашифрованный refresh token
  поддерживает versioned key rotation и чтение legacy ciphertext.
- Актуальная browser session читается без `FOR UPDATE`; блокировка применяется
  только при фактическом обновлении identity claims.
- Периодическая очистка удаляет только просроченные login transactions/sessions,
  не затрагивая активные записи.
- Проверены Viewer, Editor, Platform Admin, implicit Editor workspace `default`,
  explicit membership override и отсутствие доступа без membership.
- Integration catalog изменяет только Platform Admin.
- Actor-поля transport-моделей read-only.
- Рекурсивно запрещаются passwords, client secrets и token material, но разрешены
  `credentialRefs` и несекретные URL с `token` в имени.

### Документы и конкурентное редактирование

Табличный integration- и E2E-наборы проходят по всем 22 коллекциям:

```text
projects, tenants, environments, folders, types, queries, data-views,
compositions, stores, streams, updates, mocks, components, actions, filters,
converters, computations, vocabs, i18n-bundles, auth-profiles, navigations, styles
```

Для каждой коллекции проверяются create, list, get, patch, no-op patch, stale patch,
soft-delete, скрытие deleted, `includeDeleted`, restore, ETag, revision и server
actor. List дополнительно проходит с pagination и фильтром `active`.

Отдельно проверяются:

- malformed, trailing и неизвестные JSON-поля;
- Query `sourceVersion=2`, read-only actor и вложенный secret;
- отсутствие `If-Match` (`428`) и stale revision (`409`);
- два последовательных клиента с одним ETag: запись проходит только у первого;
- Update -> Store, Vocab -> AuthProfile и Project -> Environments через identity;
- запрет relation из другого workspace;
- запрет удаления root folder, self-parent и folder cycle;
- перенос дочерних папок и документов в root с отдельными revisions при soft-delete.

### История, commits, releases, import и backups

- Каждый lifecycle write создаёт revision; rollback не оставляет частичную историю.
- Revision restore создаёт новую revision и возвращает прежний snapshot.
- Commit plan, create, `nothing_to_commit`, preserve и squash.
- Squash физически удаляет промежуточные revisions и сохраняет contributors.
- Commit restore plan и restore создают новое состояние, не меняя старый commit.
- Release создаётся из commit; `last/export` отдаёт готовый portable JSON без replay.
- Release restore plan и restore создают новый commit, не изменяя release.
- Live domain и portable export содержат единый workspace JSON со всеми коллекциями.
- Portable JSON не содержит memberships, users, revisions, commits, releases,
  auth transactions/sessions, внутренних UUID-связей и секретов.
- Export/import/export одного portable JSON сохраняет `dv2` domainVersion;
  legacy Action/Vocab нормализуются до хэширования, а `dv1` остаётся проверяемым
  после обновления backend.
- Import plan проверяет bundle и секреты.
- Import execution требует confirmation, актуальный workspace ETag и Admin; stale
  workspace ETag возвращает стандартный `412 Precondition Failed`.
- Успешный import создаёт новые revisions и один `operation=import` commit, не
  удаляя историю. Отсутствующие в полном snapshot документы получают обратимую
  soft-delete revision, а restore родительского commit возвращает их состояние.
- Manual backup, alias `last`, JSON export и ZIP archive проверяются вместе с
  manifest и snapshot-файлами.

### Fuzzing

Fuzz targets работают без БД и проверяют отсутствие panic:

- произвольный JSON transport body и единый `4xx` для невалидного ввода;
- `If-Match`, отрицательные значения, переполнения, weak и malformed ETag;
- document create/patch inputs и explicit `null`;
- рекурсивный поиск секретов во вложенных object/array;
- portable snapshot normalization, порядок коллекций и relation validation;
- malformed JWT и произвольные token strings.

## Покрыто и не покрыто

| Область | Статус | Примечание |
|---|---|---|
| Unit/contract/architecture | Покрыто | Выполняется без Docker |
| PostgreSQL 17 migrations/repositories | Покрыто | Testcontainers, новая БД на сценарий |
| HTTP CRUD всех документов | Покрыто | In-process Fiber, без сетевого listener |
| OIDC JWT/JWKS | Покрыто локально | Локальный RSA provider |
| Реальный внешний Keycloak | Не покрыто | Нужен отдельный environment smoke test |
| Mutation testing | Не покрыто | Осознанно отложено |
| Performance/load/soak | Не покрыто | Нужен отдельный профиль и SLO |
| Production infrastructure, TLS, ingress | Не покрыто | Не относится к repository test suite |
| Реальный browser redirect через внешний IdP | Не покрыто | Проверяются adapter URL и backend session primitives |

## Добавление новой document collection

При добавлении коллекции необходимо:

1. добавить миграцию, repository port и PostgreSQL adapter;
2. зарегистрировать тип в portable registry и bootstrap-модулях;
3. добавить transport DTO, handler, routes и Swagger-аннотации;
4. добавить payload в `documentCases()` integration-набора;
5. добавить payload в `documentHTTPCases()` E2E-набора;
6. добавить collection в OpenAPI contract test и architecture ownership test;
7. если появились structured relations, добавить positive и cross-workspace cases;
8. выполнить `make docs`, `make test-unit`, затем tagged-наборы с Docker.

Не следует создавать отдельный SQLite adapter ради тестов: PostgreSQL-специфичные
JSONB, composite FK, deferrable constraints, locking и transactional semantics должны
проверяться на той же СУБД, которая используется в production.
